# Stress test - 2026-10-15T020905Z

Four layers, chosen by a council of advisers: planted-truth math, degenerate data,
concurrent load, and an idle-tab soak. **Synthetic-verified, not live-verified:** the
sandbox that ran this cannot reach Yahoo Finance or the Railway URL, so every run used
a test-only harness that patches `yfinance` with seeded synthetic prices (never
committed, never written to `data/`). The live 154-check audit (`python -m
tests.batch_audit`) still has to be run on a machine with Yahoo access.

Machine: 4 vCPU, 16 GB, Python 3.13, Streamlit 1.62.0. Load figures include headless
Chromium sharing those 4 vCPUs with the server, so they are an upper bound on wait time,
not the server's limit. Railway's vCPU is different; re-measure there before quoting a
capacity number on the live site.

## 2. Degenerate data, through the whole app (equal weight and risk parity, Sample covariance)

| basket | before | after |
|---|---|---|
| asset with a constant price (money-market fund at $1.00) | **headline "nan%", then crash** (`ValueError` at the risk-contribution panel) with Sample or EWMA covariance; "+nan" correlation in prose with Ledoit-Wolf | excluded with a stated reason; analysis runs on the rest |
| exact twin of another asset (correlation +1.00) | ok - concentration warning shown | unchanged |
| one -60% day | ok | unchanged |
| 80% of days missing | ok - common window shrinks, day count shown | unchanged |
| constant-price asset + one other | crash | "Fewer than two usable symbols" plus the exclusion reason |

Root cause: the equal-risk-contribution solver divides by each asset's variance.
Fix: `ingestion.flat_columns()` names zero-variance assets and `main.py` drops them before
any math, the same way the short-history guard drops a name it cannot use.

## 3. Load - simultaneous visitors on one process

Profile of a NEW visitor on a WARM server (every cache already filled) showed ~3s of CPU
recomputed per page view by three pure functions: signal IC 1.55s, ES bootstrap 0.84s,
Risk Topology payload 0.67s. All are deterministic, so they are now cached like the
Monte Carlo. Script CPU per warm page view: **5.08s -> 1.78s**.

| scenario | headline p50 | headline p95 | click (engine switch) p50 / p95 | page errors |
|---|---|---|---|---|
| 1 visitor, cold server | 3.6s | 3.6s | 2.6s | 0 |
| 10 at once, cold (before fixes) | 24.9s | 30.8s | 32.5s / 38.5s | 0 |
| 10 at once, cold (after) | 18.5s | 20.9s | 7.9s / 15.0s | 0 |
| 25 at once, cold (after) | 36.8s | 52.9s | - | 0 |

Server CPU per visitor (page load + one click), from /proc sampling: **6.5s -> 4.5s**.
All 25 simultaneous visitors were served; peak memory 716 MB. One early run logged 9
browser page errors whose text was not captured; two reruns with capture on logged 0.

## 4. Soak - idle tabs

| 15 tabs open, idle | server CPU (mean) | memory |
|---|---|---|
| before (freshness caption ticking every 1s) | **92.7% of a core** | 498 -> 508 MB over 10 min |
| after (ticking every 60s) | **4.1%** | 489 -> 489 MB over 5 min |

Each tick costs the process ~60ms; at 1 Hz, 15 idle tabs kept it busy doing nothing and
every new visitor queued behind them. The caption now counts minutes. No memory growth.

## Capacity, plainly

On this machine one process serves ~10 simultaneous first-time visitors with the last
headline at ~21s, and 25 with the last at ~53s; idle tabs now cost almost nothing. The
next lever, if a spike ever stalls the live site, is a process-wide cap on concurrent
simulations (RUNBOOK.md section 4) - not a proxy.
